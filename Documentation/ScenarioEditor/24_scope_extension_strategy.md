# Scenario Studio 拡張スコープ検討メモ

作成日: 2026-05-12

## 位置づけ

これは「今すぐ全部実装する」ための仕様ではなく、様々な環境での動作、複数人での共同執筆、ゲーム連携、ゲーム外用途、フレーバーテキスト管理まで広げる場合の判断資料である。

結論として、Scenario Studio の中核は「創作プロジェクトの構造化データを壊れにくく編集すること」に置き、ゲームエンジン別連携、共同編集、用途別出力は外側のプロファイルやアダプタとして増やすのが安全。

## 課題感

- ブラウザ、デスクトップ、Unity など実行環境ごとにファイルアクセスとセキュリティ条件が違う。
- 複数人で共同執筆する場合、リアルタイム編集より先に、差分が読めて競合を直せる保存形式が必要になる。
- ゲーム用途では Unity、Godot、RPGツクール、独自エンジンなどで期待する形式が違う。
- ゲーム外用途では小説、TRPG、企画書、レビュー資料、翻訳、ボイス収録台本など、必要な出力が変わる。
- フレーバーテキストは脚本セリフと性質が違い、アイテム、場所、キャラ、UI文言、クエスト説明などに紐づく短文資産として扱う必要がある。

## 基本方針

### 1. 中核データは用途非依存にする

中核には、シナリオ、チャプター、シーン、キャラ、場所、用語、関係性、テキスト資産を置く。Unity 専用、Web 専用、小説専用のフィールドは中核に直接混ぜない。

ゲーム固有の都合は、エクスポートプロファイル、テンプレート、外部アダプタ側で吸収する。

### 2. ID と表示名を分離する

表示名は自由に変更できるものとして扱う。参照には安定 ID を使い、必要なら内部で `ch_001`、`sc_001`、`node.xxx` のような識別子を持つ。

共同作業やゲーム出力を考えると、表示名を参照キーにすると後で破綻しやすい。

### 3. ファイルは差分に強くする

巨大な単一ファイルに寄せず、チャプター、シーン、ノード、関係性、グラフ位置、テキスト資産を適度に分ける。Git や共有フォルダでも人間が競合を直せる YAML/Markdown/JSON を優先する。

まずはリアルタイム共同編集ではなく、「競合しても直せる」「誰が何を変えたか追いやすい」形を目指す。

### 4. 出力はプロファイル化する

中核データから以下のような出力を作る。

- ゲーム用 JSON
- Unity ScriptableObject 生成用データ
- Godot / 独自エンジン向け JSON
- Markdown 台本
- ボイス収録台本
- レビュー用 HTML
- 翻訳用 CSV
- フレーバーテキスト一覧

本体 UI にエンジン別の事情を直接増やすより、出力プロファイルを追加できる形にする。

## フレーバーテキストの扱い

フレーバーテキストは脚本ブロックではなく、テキスト資産として扱うのがよい。

候補:

```yaml
id: text.item.short_sword.description
owner:
  kind: node
  id: node.short_sword
purpose: item_description
locale: ja
text: 古びているが、手入れの行き届いた短剣。
tags:
  - ui
  - inventory
```

この形にしておくと、アイテム説明、場所説明、キャラ紹介、UI文言、クエスト文、ロード画面文、収録用セリフなどを同じ仕組みで扱える。

## ノードベースのプロット / 脚本メモ

プロットや脚本メモは、シーン本文だけに閉じ込めないほうがよい。実際の物語は、主筋、サブプロット、キャラアーク、謎、伏線、感情線が同時並行で進み、1 つのシーンが複数の流れを同時に進めるためである。

この用途は、既存のグラフ機能を発展させた `プロットボード` として扱う。`Plot Flow Lens` は既存シーンの遷移を読む機能、`プロットボード` はまだ脚本化されていない筋やメモをノードとして作る機能、と役割を分ける。

詳細設計は `25_graph_plot_board.md` に分ける。中核方針としては以下。

- プロットボードは `Scenarios/` ではなく `PlotBoards/` に保存する。
- ノードには安定 ID を持たせ、表示タイトルは自由に変更できるようにする。
- プロットノードはチャプター、シーン、キャラ、場所、用語へアンカーできる。
- 1 つのプロットノードが複数のプロットスレッドに属せるようにする。
- 脚本本文への完全な行単位リンクは、脚本ブロックに安定 ID を導入してから扱う。
- Review HTML や AI handoff には、関連プロットノードを文脈として渡せるようにする。

## 共同執筆の段階案

### 段階 1: Git/共有フォルダで壊れにくくする

- ファイル分割を明確にする。
- 安定 ID を徹底する。
- 保存対象を明文化する。
- 差分が読みにくい自動整形を避ける。
- プロジェクト診断で参照切れ、重複 ID、未保存データを検出する。

### 段階 2: 競合支援を入れる

- 変更履歴を UI で見せる。
- シーン単位、ノード単位の変更差分を表示する。
- 同じファイルの同時編集を警告する。
- 自動マージできる項目と手動確認が必要な項目を分ける。

### 段階 3: リアルタイム共同編集を検討する

リアルタイム共同編集は最後でよい。Yjs/CRDT などは有力だが、UI、権限、履歴、オフライン復帰、競合説明が必要になり、実装コストが大きい。

## ゲーム連携の段階案

### 段階 1: エクスポートを安定させる

まずは中立 JSON、Markdown、CSV を安定出力する。

### 段階 2: Unity 連携を外部アダプタにする

Unity では Scenario Studio の中核データを読み、ScriptableObject や Localization Table に変換する。Scenario Studio 本体を Unity 専用設計にしない。

### 段階 3: 他エンジン向けプロファイルを追加する

Godot、RPGツクール、独自エンジンは個別プラグインやエクスポートプロファイルとして扱う。

## ゲーム外用途

ゲーム外用途は、エディタ本体の中核を広げすぎず、テンプレートと出力で吸収する。

- 小説: 章、シーン、登場人物、場所、時系列
- TRPG: NPC、場所、イベント、ハンドアウト、情報項目
- 企画: 世界観資料、キャラ表、関係図、用語集
- 翻訳: キー付きテキスト、コメント、文脈
- 収録: 話者、セリフ、感情、尺、ファイル名

## やらないこと

- 中核データを特定ゲームエンジン専用にしない。
- 最初からリアルタイム共同編集を目標にしない。
- フレーバーテキストを脚本セリフに無理に混ぜない。
- 保存形式を巨大な単一ファイルに寄せすぎない。
- 表示名を参照 ID として扱わない。

## 近い実装候補

1. 保存対象一覧を明文化し、プロジェクト診断に加える。
2. テキスト資産 `Texts/` を追加する。
3. エクスポートプロファイルの設定ファイルを追加する。
4. Unity 向け出力をプロファイルとして切り出す。
5. 共同執筆向けに「変更されたファイル一覧」と「競合しやすいファイル」を見せる。
6. プロットボード `PlotBoards/main.board.yaml` を追加し、グラフ上で保存できるプロット / 脚本メモを扱う。
